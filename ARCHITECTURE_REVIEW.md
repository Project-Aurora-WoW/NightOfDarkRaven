# Night of the Dark Raven — ревью архитектуры серверной части

Дата: 2026-11-11
Область: `server/src`, `server/sql`, `*.conf`, `init_db.sql`, сборка CMake, `test_client.py`.

## 1. Что есть сейчас

Три сетевых процесса на C++20 + Winsock, один общий каркас сессий и SQL-схема на MySQL 8.

| Компонент | Порт | Состояние |
|---|---|---|
| `authserver` | 3724 | **не реализован**: `main.cpp` — только `#include`, нет `main()`, нет логики |
| `worldserver` | 8085 | примитив: PING работает, авторизация сравнивает один 32-битный токен из файла, вход в мир отдаёт константы |
| `registerserver` | 8080 | реальная HTTP-регистрация аккаунта (SRP6 salt/verifier в БД), но с SQL-инъекцией |

Общий код: `ByteBuffer` (LE-сериализация), `Session`/`Acceptor` (select-цикл), `SRP6.h` (только генерация verifier), `AuthShared.h` (токен в файле).

Протокол: `u16 bodySize | u16 opcode | body`, little-endian. Один TCP-поток на процесс, неблокирующие сокеты, `select()` с таймаутом 100 мс.

### Ключевой вывод

**Доверие в системе полностью отсутствует.** Клиент присылает `u32 token`, сервер читает одно число из `authShared.txt` и сравнивает.:
- токен не привязан к аккаунту — любой, кто знает число, входит;
- токен не одноразовый и не истекает;
- файл общий для всех клиентов, то есть «сессия» одна на весь сервер;
- `CMSG_PLAYER_LOGIN` вообще не требует авторизации: тестовый клиент логинится персонажем, ни разу не пройдя auth;
- пароль в `authserver` не проверяется, потому что сервера нет.

То есть SRP6-хранилище наполнено корректно (`registerserver` считает verifier), а сверить с ним никто не умеет. Это главный разрыв, который надо закрыть.

## 2. Критические дефекты

### 2.1. `authserver` пуст
`server/src/authserver/main.cpp` — 22 строки включений, нет `main`. Цель сборки `authserver` создаётся из одного этого файла → линковка должна падать. Собранные `.exe` в `build*/` — от более раннего состояния кода.

### 2.2. SQL-инъекция в `registerserver`
`registerserver/main.cpp`, `HandleRegister`:
```cpp
std::string checkQuery = "SELECT id FROM ndv_auth.account WHERE username = '" + username + "'";
```
`username` берётся прямо из JSON-тела запроса. `username = "' OR '1'='1"` или `"x'; DROP TABLE ...; --"` — исполняется. Проверка длины `> 32` не спасает. Нужен prepared statement, как в соседнем `INSERT` (он сделан правильно).

### 2.3. Утечки памяти в `MYSQL_BIND`
```cpp
bind[0].length = new unsigned long(username.size());
```
Четыре `new unsigned long` на каждый регистрационный запрос и ни одного `delete`. Растёт линейно с числом регистраций. Для `length` достаточно указателя на локальную `unsigned long`.

### 2.4. Битый seed-аккаунт `raven`
В `init_db.sql` и `initial_db.sql` verifier для `raven` = 64 нулевых байта (`UNHEX('000...0')`). Это математически невозможно: `v = g^x mod N ≠ 0`. То есть «дефолтный аккаунт `raven`/`raven`» из README **не может пройти SRP6-проверку**, как только она появится. Нужно пересчитать verifier (это делает `registerserver`, либо отдельная утилита).

Плюс в `initial_db.sql` hex verifier'а **63 символа** вместо 64 — `UNHEX` вернёт `NULL`, а колонка `NOT NULL`.

### 2.5. `authShared.txt` — 4 байта мусора
`readSharedToken()` читает `uint32_t` из файла; содержимое файла — `BD 5E 60 9D`-подобный случайный мусор. Формально читается, но это не токен, выданный authserver. Файловый канал auth→world не сериализован: два одновременно зашедших игрока затрут токен друг друга (`trunc` + `write` без блокировки).

### 2.6. `worldserver` не проверяет `_authed`
Поле `bool _authed = false;` объявлено в `WorldSession` и **никогда не читается**. `CMSG_PLAYER_LOGIN` обрабатывается для любого подключения.

## 3. Дефекты среднего уровня

### 3.1. `Network.h`
- **Медленный клиент блокирует весь сервер.** `TrySend()` вызывается и когда сокет не готов к записи (`if (!dead && s->HasPendingWrites()) s->TrySend()`). `send()` на неблокирующем сокете вернёт `SOCKET_ERROR`/`WSAEWOULDBLOCK`, и код считает это смертью сессии (`return false`). Под нагрузкой или при медленном клиенте соединения рвутся произвольно. Нужно различать `WSAEWOULDBLOCK` и настоящую ошибку.
- **Бесконечный рост очереди.** `Send()` кладёт кадр в `_writeQueue` без лимита; клиент, который не читает, съест память.
- **`Send()` не просыпает `select`.** Фрейм ставится в очередь, а цикл `select` может спать до 100 мс; отдельный флаг «есть неписанное» не проверяется при формировании `writeSet`, хотя повторная попытка ниже это компенсирует — работает, но неявно.
- **Нет лимита размера кадра.** `size` из сети до 65535, буфер 8192 → присланный кадр `size=60000` навсегда застрянет: `_recvLen < 4+size` истинно, буфер полон, `ProcessFrames` крутится вхолостую. Полуоткрытое соединение-залипание (DoS на слот).
- **`maxSock + 1` для `select`** — допустимо на Windows, но при `SOCKET_MAX`/больших дескрипторах `static_cast<int>` некорректен; и лимит `FD_SETSIZE` (64 по умолчанию) не проверяется при `FD_SET` — переполнение fd_set при >64 сессиях.
- **Обработчик исключения возвращает `false`** — то есть любое неверное поле в пакете (в т.ч. `ByteBuffer underflow`) убивает соединение. Логируется через `std::cerr` без метки времени и IP.
- `_running` — неатомарный флаг, читается/пишется из потока accept-цикла; сейчас один поток, но `Stop()` из другого потока небезопасен.
- `TryRecv()` читает `FIONREAD`, но при `space <= 0` возвращает `true`, т.е. бесконечно «здоров».

### 3.2. `ByteBuffer.h`
- `operator>>(std::string&)` читает до NUL **без ограничения длины**: пакет из 8000 байт без NUL — нормально только если `need()` выбросит `out_of_range`; но строка конкатенируется побайтно, `v.push_back` на каждый байт — лишние аллокации. Ограничение `maxLen` обязательно.
- `operator<<` для `bool`: `std::is_arithmetic_v<bool>` — true, пишется как `sizeof(bool)` = 1 байт. Совпадает с ожидаемым `u8`, но в коде уже пишут `uint8_t(...)` явно — непоследовательно.
- `need()` объявлен `const`, но меняет `_r` в вызывающей ветке — ок, но `_r` не сбрасывается при повторном чтении; нет `reset()`/позиции для повторного разбора.
- Little-endian предполагается у хоста; на x86/x64 Windows верно, в комментарии это честно записано, но `static_assert` для размера `T` нет.

### 3.3. `SRP6.h`
- **`static BIGNUM*` в заголовке** — по копии на каждую единицу трансляции, при этом `nullptr`-инициализированы и инициализируются лениво. Это не потокобезопасно и в каждом TU свой указатель. Нужен `inline` (C++17) или singleton-функция.
- **`BN_hex2bn((BIGNUM**)&SRP6_N, ...)`** — приведение `BIGNUM**` → `BIGNUM**` от `BIGNUM* const`, работает, но избыточно и опасно; `BN_hex2bn` сам аллоцирует — исходное `BN_new()` **утекает**.
- **`rand()` для соли** — предсказуемо, `srand` нигде не вызывается. Соль должна быть из `RAND_bytes` (OpenSSL уже линкуется).
- **Неполный SRP6.** Есть только verifier. Нет `SRP6_CalculateU/S/M`, нет серверного `b`, `B`, `S`. То есть даже при наличии verifier'а сервер не сможет провести handshake.
- **Односторонняя нормализация.** `SRP6_H1` применяет `Utf8ToUpperOnlyLatin` к паролю. В TrinityCore нормализуется **только имя пользователя**, пароль берётся как есть. При текущем коде клиент, повторяющий TrinityCore, получит несовпадающий verifier.
- `SHA_CTX`/`SHA1_Init` — устаревший OpenSSL 1.x API; в OpenSSL 3 всё ещё работает с deprecation-предупреждениями. При `OPENSSL_FOUND` в CMake линкуется и `SSL`, и `Crypto` — `SSL` не нужен.

### 3.4. `registerserver`
- Один глобальный `MYSQL*` без пула; конкурентность нулевая (однопоточный accept-цикл с блокирующими 2-секундными таймаутами) — **любой медленный клиент стопорит регистрацию всем**.
- `JsonGetString` — регекс-подобный разбор без учёта экранирования: `{"password":"a\"b"}` разберётся неверно; нет валидации JSON вообще.
- HTTP: `Content-Length: ` ищется литерально с учётом порядка заголовков и `atoi` без проверки ошибок; `Transfer-Encoding: chunked` не поддерживается; ответы с `Access-Control-Allow-Origin: *` для регистрации.
- Нет ограничения частоты — регистрация ботом тривиальна.
- Пароль возвращается клиенту в ответе? Нет, но **salt и verifier уходят в JSON-ответ** — это лишнее, для клиента SRP6 salt нужен, но verifier серверу-клиенту отдавать не следует.
- C++-креды: `root`/`root` захардкожены, плюс fallback «попытка без пароля».
- `username` не нормализуется (`raven` и `Raven` создадут две записи в `utf8mb4_0900_ai_ci`? нет — ci-коллация их склеит → конфликт с 409, но `SRP6_H1` всё равно нормализует в upper — расхождение между БД и алгоритмом).

### 3.5. Конфигурация
- `authserver.conf`: секция `FallbackAccounts` **объявлена дважды** (`[Misc]` и `[Language]`), в конце файла приклеен мусор `E C H O   i s   o n .` (это UTF-16LE обрывок — файл был склеен из двух кодировок).
- `gameserver.conf` целиком в UTF-16LE с BOM — не читается стандартным `std::ifstream`/ini-парсером; и в нём `DBName = ndv_world` для секции `[Characters]`, хотя отдельной БД `ndv_characters` не существует.
- **`authserver.conf` никем не читается**: ни один сервер не имеет парсера INI. Все значения захардкожены (`8085`, `root`/`root`, порт 3720/3724 отсутствует вовсе).
- `realm` в конфиге указывает порт 8085, `worldserver` слушает 8085 — согласовано.
- `MaxConnections`, `SocketTimeout`, `SessionTokenTTL`, `MaxFailedAttempts`, `LockoutDurationMinutes` — объявлены, не используются. Логин не блокируется после неудач (brute-force).

### 3.6. SQL
- Три источника схемы: `init_db.sql` (корень), `server/sql/initial/initial_db.sql`, `server/sql/base/*.sql` — и они **различаются**: `initial_db.sql` использует `utf8mb4_0900_ai_ci`, `init_db.sql` — `utf8mb4_unicode_ci`; в `characters_init.sql` `uk_account_name` объявлен как `KEY` (не `UNIQUE`), в `init_db.sql` — как `UNIQUE`; `DROP TABLE IF EXISTS characters` перед созданием — разрушительно при повторном запуске.
- `characters_init.sql` **не содержит `CREATE TABLE characters` до `INSERT`** в первых строках: `INSERT` идёт раньше `CREATE TABLE` по тексту файла (порядок перемешан), а `CREATE PROCEDURE` с `USE ndv_world` — после `DROP`.
- `sp_create_character`: `p_class NOT IN (1,2,3,4,5,5,6,...)` — дубликат `5`, значения валидации неполны.
- Нет процедуры/отдельной утилиты для пересчёта verifier'а у seed-аккаунта.
- `authShared.txt` в корне репозитория — рабочий файл, а не артефакт.

### 3.7. Сборка и репозиторий
- `main.obj` в корне, `build/` и `build_server/` полностью закоммичены по факту наличия в папке (проверить `.gitignore` — он есть, 3.9 КБ, но артефакты уже лежат вокруг него).
- `CMakeLists.txt` верхнего уровня — 3 строки, `add_subdirectory(server)`. Нет `find_package(OpenSSL REQUIRED)`, хотя `SRP6.h` использует OpenSSL **безусловно** — при `OPENSSL_FOUND=false` сборка упадёт на `#include <openssl/sha.h>`.
- Пути к MySQL (`C:/Program Files/MySQL/MySQL Server 8.0/...`) захардкожены в `server/CMakeLists.txt`; при переносе на другую машину не собирается.
- `#pragma comment(lib, ...)` дублирует `target_link_libraries` — расходится (`authserver` в CMake линкует `libmysql`, но не `libcrypto` для `.lib`-явной ссылки).
- `_WIN32_WINNT` определяется в `authserver/main.cpp` как `0x0501`, а в CMake — `0x0A00`; при `windows.h` из `mysql.h` до `#define` возможна рассинхронизация.
- `server/src/gameserver/gameopcodes.h` и папка `gameserver` — не собираются, дублируют `Opcodes.h`.
- `ops_new.txt` в корне — полный `Opcodes.h`, который **должен быть** в `server/src/common/Opcodes.h`; сам `Opcodes.h` содержит только `eAuthClientOpcode`.
- `write_authserver.js` мешает пользователю записать `main.cpp` — это генератор, оставленный в корне.
- `client/` собирается отдельно и в этом репозитории нет UE-кода; `README` ссылается на `client/Source/NightOfDarkRaven/NDVOpcodes.h`, которого нет.

## 4. Рекомендуемая целевая архитектура

```
                    ┌──────────────┐
  клиент ──3724──▶  │ authserver   │──▶ MySQL ndv_auth.account (+ realmlist)
                    └──────┬───────┘
                           │ выдача одноразового токена (accountId, expiry), 
                           │ хранение в MySQL/redis, НЕ в общем файле
                           ▼
                    ┌──────────────┐
  клиент ──8085──▶  │ worldserver  │──▶ MySQL ndv_characters
                    └──────────────┘
                    ┌──────────────┐
  HTTP  ──8080──▶   │ registerserver│──▶ MySQL ndv_auth (prepared statements)
                    └──────────────┘
```

Принципы, которые надо зафиксировать:
1. **Аутентификация — только по SRP6** (полный handshake: salt, B, сходимость M1/M2), verifier в БД.
2. **Токен = Py server-side session**: `accountId + expiry + random 256-bit`, одноразовый, удаляется при погашении. Файловый обмен допустим только как dev-заглушка с блокировкой и `RAND_bytes`.
3. **Каждое world-сообщение кроме `CMSG_WORLD_AUTH` требует активной сессии** (`_authed` + привязка сессии к accountId/characterGuid).
4. **Один писатель схемы**: `server/sql/base/` — источник истины, `initial_db.sql`/`init_db.sql` — сгенерированные или удалены.
5. **Конфиг единственный и читаемый**: один парсер INI, одна кодировка (UTF-8 без BOM), без секретов в репозитории.
6. **Сетевой слой не убивает соединение на `WSAEWOULDBLOCK`**, имеет лимит кадра, лимит очереди и таймаут.

## 6. Что учтено при доработке

По ходу правок внесены точечные исправления, не ломающие текущий протокол `u16|u16`:
- `authserver` реализован и собирается;
- токен стал 64-битным, генерируется из `RAND_bytes` и хранится в БД (`ndv_auth.session_token`), с TTL;
- `worldserver` проверяет токен по БД, привязывает сессию к аккаунту, не пускает `CMSG_PLAYER_LOGIN` без авторизации и читает персонажа из БД;
- `Session` больше не считает `WSAEWOULDBLOCK` смертью и ограничивает размер кадра и очередь.

Остаются как известный технический долг: полный SRP6 handshake (`M1/M2`) — реализована серверная часть, но нужен парный клиентский код в UE-клиенте; парсер INI; пул соединений MySQL.
